# Execution metadata corrections

The frozen pilot protocols inherit fields from the earlier two-model short-input study. They are retained byte for byte because their hashes are recorded in every result. The following clarifies execution using the accompanying driver source; it does not discard or reclassify measurements.

- All studies in this directory execute Qwen3 only. Inherited Qwen3.5 adapter, restoration and failed-method fields do not describe work performed here.
- For the alternating three-mode pilots, `original_repeats` and `additional_warm_core_repeats` are inherited labels. The actual driver schedules one complete warm call per mode and input length, then three complete measured calls per mode in forward/reverse/forward order, then one separately charged audit call per successful cell. Some diagnostic drivers explicitly reduce that schedule or add separately recorded controls/profiling. Their source and raw row `phase` fields give the actual counts.
- Pilot modes share one model process to compare arithmetic on the same inputs and compiler state. The final confirmation methods each use an isolated model process. Every GPU job runs serially.
- The 128/256/512/1024 labels are the author's requested input lengths. Formatted prompt plus fixed 32 output tokens and EOS actually totals 158/265/478/905 tokens in this study. No sequence is truncated to satisfy the <=1024 requirement.
- No pilot runs FT, IG, generation or quality scoring. Their inherited configuration fields pin the author environment; they do not count as executions. The confirmation queues explicitly run both fixed FT variants.
- The whole finite graph candidate keeps one persistent geometry, including static input buffers and its graph pool. The older root-tape module docstring's statement about no cross-invocation cache applies to the root tape itself. The graph controller explicitly refreshes every graph input and recomputes the result on every call; it does not memoize attribution results.
- Whole graph v1 failed its first capture and then exposed a poisoned-cache error. V2 stops after the first failed call, never caches an incomplete graph, warms on the capture stream, and fixes the inner timer to finish after CPU conversion. Original outer complete-call timing remains authoritative for every version. V2's full traceback locates the capture failure in the existing seed wrapper's Boolean GPU read. V3 moves that same compiled Boolean to strict validation before return, explicitly counting it as the 829th predicate. No failed call is a valid latency observation.

For capture lifecycle background, see the [PyTorch graph API](https://docs.pytorch.org/docs/stable/generated/torch.cuda.graph.html) and [CUDA semantics](https://docs.pytorch.org/docs/stable/notes/cuda.html#cuda-graphs). The installed version and native sources are pinned in each raw environment record; documentation for newer versions is not a claim that a newer API was used.
