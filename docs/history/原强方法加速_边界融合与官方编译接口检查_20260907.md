# 原强方法：边界融合与官方整图编译接口检查

本阶段承接已完成的诊断成本分离、MLP 有限规则融合，不替换质量较强的整网有限差方法。边界融合三条原样本已完成；随后尝试直接复用安装的 torch.compile/Inductor 编译原生投影接口，发现实际安装环境的编译兼容错误。用户之后将 PV 交互规则比较设为优先级1，已准备的官方 bmm 适配探针暂未运行。

NI2 在本批仍慢于 FT 约0.96%，所以三条成本并未全部通过。前批 NI2 相对 FT 慢约11.8%，不能把差距从11.8%降到0.96%全部归功于本次优化：FT自身的当批耗时也变了。可归于同次对照的 NI2 改善是2.96%。这也是后续 PV 实验把 FT 测时穿插到每轮候选之后的原因。

融合原公式中的五组操作：端点平均、QK缩放加概率及原审查、GQA归并加缩放与旋转、两分支加和接有限RMSNorm与残差、三分支加和接有限RMSNorm与残差。全部使用安装的 Inductor 自动生成执行核，原矩阵乘法、模型与 FA 保持。独立源码检查证明恢复提取片段后与上一版源码 AST 相同；未使用的原始缩放分数返回槽改为 None，经检查下游从未消费。

NI0/NI2/MH0 新带符号向量相对旧版 L2 分别约0.01288%、0.02220%、0.02605%，反号 token 均为0。恢复率和RISE保持，MAS分别变化+0.00000335、+0.00000191、−0.00001725。删除mask和原始曲线有微小差异，不能称数值完全相同。所有三条新评分向量均重新运行原21点删除曲线，共63次评估前向；另27条同完整向量曲线沿可核实来源链复用。四次重复结果与两次额外profile均计入研究开销。

本阶段有两份profile，分别为NI0、NI2。每份有72次实际原生FA前向、253次原生FP16归因投影；144次平均、72次缩放概率、36次布局、36次两分支归一化残差和36次三分支归一化残差均链接到实际执行的编译核。额外六份profile属于后续PV实验，不计入此阶段。

正常路径继续不采集逐算子FP64诊断账本，字段为None。实际目标差、signed sum 和未分配残差保留；三样本未分配相对残差约0.01828%、0.14329%、0.16963%。这不是新的负向删除因果认证。

用户希望尽量整体复用已有自动加速，而非继续逐项手写算子。为检查完整图的投影接口，直接对原生 `native_half_linear` 调用 `torch.compile(...,fullgraph=True,backend='inductor')`，在实际NI0第35层MLP down投影输入上测试。安装版本在 `torch.mm(...,out_dtype=torch.float32)` 的 fake tensor 元数据阶段报 `meta_mm() takes 2 positional arguments but 3 were given`。无完成的编译输出或编译GPU执行证据。原生投影已先计算，探针始终把原结果继续传回原归因；253次原投影、完整最终向量均核实未变。没有patch全局meta、编译后端或GEMM内核。

这仅证实该安装环境的 mm.dtype 编译接口问题，不等于所有官方自动编译都不可用。原生bmm增加一个长度1的批维是已准备的另一路接口适配，但尚未执行，不能当作已加速成果。[上游同类问题](https://github.com/pytorch/pytorch/issues/163275) 与 [torch.compile 官方说明](https://docs.pytorch.org/docs/2.8/generated/torch.compile.html) 提供相应接口背景；实际本机结论以保存的真实输入、失败栈和源码为准。

边界融合PID89844与编译接口探针PID95568均已结束。前者116物理根前向/3反向参照/26归因/936额外原生层重算（其中63前向为原评估）；后者1物理批量根前向/0反向/1归因/36额外批量层重算。探针不算质量基准，也不把局部编译尝试当作正常API耗时。下一步已按用户新优先级转到三种PV规则的固定原16条检验，未在同一候选中混入编译接口修改。
