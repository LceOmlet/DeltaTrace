# Qwen3.5 真实 FA/FLA 前向与批处理差异

Qwen3.5-9B 已用共享官方权重完成 NI0/MH1 的两个 B1 和一个异长 B2 原生前向，实际经过 FLA、厂商 FA 和 causal-conv 内核。新模型归因尚未实现；B1/B2 数值筛查没有通过，也未做质量或生成测试。

## 修正了什么

第一作业完整加载权重后，被作者总模块无关的 wordfreq 导入拦住，前向为零。现在从固定哈希的作者源码 AST 原样加载文本准备类及两个常量，调用作者 `target_response`；没有复制或替换模型实现。新输入保持原模板、固定 target 加 tokenizer EOS、PAD=EOS=248046。NI0 的输入/目标长度为605/248，MH1为368/141；字符偏移与作者用户 token 位置完整相符，没有边界合并。旧词表的 gold 和生成下标尚未重映射。

第二作业在首层真实 FLA 状态更新处失败：共享内存要求76288字节，硬件上限65536。检查安装的官方 FLA0.4.1 后，只把该内核的自动调度候选 `num_stages=[2,3,4]` 改成 `[1]`，其余代码原样保留。相关 MetaX 社区记录也报告了同类故障，但它使用不同的 vLLM 栈，不能替代本机验证：[原始问题记录](https://github.com/flagos-ai/vllm-plugin-FL/issues/93)。

适配限于已经隔离的环境，有原始文件备份与前后哈希；完整函数体 AST 和反向代码不变。安装后2853个 Transformers/FLA 源文件重新比对，只允许此前设备名称映射和这次调度列表两处文件差异。任务结束后的只读审查再次确认源码及权重大小/mtime未变。这里没有再次读取20GB权重重算哈希，完整权重身份承接此前的官方LFS核验。

编译缓存中，原12个状态内核配置的共享内存均在76288—91136字节；4个单阶段配置在16384—25600字节。这些元数据包含尝试过的配置，不单独证明每次执行选中了哪个配置。实际第三作业则完成了全部三个前向，证明这次调度修改解决了所见资源失败；没有回退到 Torch 模型路径。

## 原生执行证据与数值范围

每个完成的前向均有24次 FLA chunk、24次 causal-conv 和8次公开 FA 调用，32个原生层顺序完整，未替换 model.forward。NI0 与 B2 的 GPU trace 均确认实际 FLA 状态内核及8个主要 FA 内核；不是仅根据配置或 Python import 判断。

一个值得跟进的具体差异是：**NI0 B1 的默认 FA 选择 split-KV，加8个合并内核；B2 的 varlen FA 选择普通前向内核。** 因此批处理改变了原生 FA 内部计算路径。这个证据提供了数值差异的候选来源，但尚未排除 GEMM 形状、FLA 或其他逐层影响，不能据此宣称因果定位完成。

| B1 与 B2 的完整目标 log-prob 比较 | NI0 | MH1 |
|---|---:|---:|
| target token数，含EOS | 248 | 141 |
| 平均绝对差 | 0.010171 | 0.009300 |
| 最大绝对差 | 0.233608 | 0.220143 |

| B1目标log-prob总和 | -109.28824 | -62.21851 |

事前的相对1%筛查失败，绝对0.25筛查通过。这是工程诊断标准，并非官方精度保证，也不是“超过1%就是实现错误”的证据。继续遵循用户接受 FA 默认精度的要求：不追求逐位相同，不把阈值触发自动升级为FP32需求，更不事后放宽阈值冒充原筛查通过。

三个调用峰值 allocated 显存约19.68/19.35/19.98GB，均只是原生前向，不能当作归因显存。26.43/10.46/13.25秒包含首次形状编译或自动调优，其中第一和第三个还含 profiler；没有充分预热的同次耗时对照，不报告稳定吞吐或与8B/FT的速度比。NI预热trace有927个状态内核事件，B2有24个；前者包含官方自动调优，不能把927误说成927次模型调用。

还发现一个实验编排问题：第一例的 batch 断言提前退出，使第二例比较没有写入原比较列表，也跳过了预定CPU参考核验及前缀数组保存。全部两例的目标向量已经在各调用结果中保存，后续CPU分析重算了两例完整差异；没有额外模型调用。**CPU参考实际执行为零，不能宣称局部数值参考通过。** 下一次诊断必须先持久化必要端点，再计算所有比较，最后汇总门槛。

## 方法设计推进与下一步

[有限传播设计合同](../qwen35_finite_extension_contract.md) 给出了门控状态递推的精确双端点分解：内容沿实际输入端点的状态动力学传播，衰减、写入强度和路由变化分别保留。推导表明，状态到状态的余切转移与原生端点1的反向转移相同；局部参数项则需要端点0状态。这为复用FLA原有状态反传提供了具体依据，但还没有实现 chunk 扩展，也没有速度或质量结果。

本轮四次实际前向尝试预算已关闭：三次模型加载、一次失败前向、三次完成前向；73次FLA API调用、24次FA API调用；零归因、零质量曲线、零新生成，CPU参考为零。三作业内部记录时长合计约184.50秒，不含启动前准备和之后打包传输。全部任务已结束，不能将其记为继续运行。

下一步单独冻结最多两次原生前向诊断（NI0 B1、NI0/MH1 B2）：在门槛前保存逐层数据及真实首层FLA前缀，用官方CPU参考检查跨chunk边界；对同一组真实Q/K/V增加至多一次公开FA varlen调用，与已捕获的B1 dense输出比较。先定位默认混合精度和内核分派影响，再决定是否需要修正。保留BF16默认模型，不重开质量扫描。gold重映射、FLA有限归因、完整归因成本与独立质量目标继续。

证据：`qwen35_native_preflight_summary_20260908.json`、三个固定作业原件及调度收据、`qwen35_native_postflight_20260908_v1`。第三作业原始结果 SHA256 为 `f745bdc61ddd9fb305c487512737028d256b8c3630ac2a86d409072944d6e3ae`；公开派生文件路径脱敏，原始与公开哈希分别记录。
